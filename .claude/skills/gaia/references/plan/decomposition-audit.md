# Decomposition audit

The `/gaia-plan` step 4.6 audit. The gauge in `plan.md` decides the decomposition, contract and SPEC coverage lenses; the test-design lens and its refuter run on every plan with a table. `.claude/skills/gaia/references/spec/lens-dispatch.md` is the lens contract: the shared preamble, the findings file each lens writes, and the pre-clear, classify and re-dispatch steps. This file owns which lenses run and how their findings are applied.

Contents: `## What the audit checks`, `## 4.6a. Dispatch the lens auditors`, `## 4.6a-ii. Refute the test-design findings`, `## 4.6b. Apply findings`.

## What the audit checks

A lightweight multi-agent audit of the **decomposition itself**: the one artifact neither the upstream SPEC audit (which ran before the plan existed) nor the downstream pre-merge Code Audit Team audit (which sees the executed diff) can inspect. It verifies that the task graph is a sound factoring of the work, that the frozen interface contracts resolve against the real repo, and that the SPEC's binding criteria are all covered, BEFORE a cold orchestrator burns execution cycles building against a flawed plan.

The audit stays narrow: four checks that exist only at plan stage. The decomposition, contract and SPEC coverage findings are checkable and binary, so they get no refutation pass; the test-design lens is the exception, because its findings are judgment (a layer, a duplicate, a flag), so each material one is refuted (`## 4.6a-ii`). It dispatches the same parallel `general-purpose` Agent primitive step 4 uses, so it works headless and in auto mode.

## 4.6a. Dispatch the lens auditors

1. Choose the lenses. The **Test design** lens always runs on a plan with a table, whatever the gauge. The **SPEC coverage** lens is dispatched only when `SPEC_PATH` was set in step 1a and the gauge runs the other lenses; those, **Decomposition & dependency soundness** and **Contract grounding**, run when the gauge says the plan is non-trivial. A SPEC-less plan's undispatched SPEC coverage lens is recorded not-applicable, never as a no-op.
2. Clear and create the findings directory `<PLAN_DIR>/audit/`, spelled repo-relative as the contract's pre-clear step does: `rm -rf <repo-relative PLAN_DIR>/audit`, then `mkdir -p <repo-relative PLAN_DIR>/audit` (for example `.notebook/plans/<PLAN-NNN>/audit`, or `.notebook/specs/<SPEC-ID>/plan/audit` for a spec-derived plan).
3. Spawn **one `general-purpose` Agent per lens, all in parallel** (one message, one Agent tool call per lens). Each prompt is the contract's shared preamble filled from its plan column (including its rule that, in a linked worktree, the lens writes its file with `Bash` at the main-checkout path (the clone's primary working directory, on any branch) and reads it back), with `<repo_root>` = `$PWD` and `<FINDINGS_DIR>` = `<PLAN_DIR>/audit/`, then the `LENS:` line and the lens's focus text below. Each lens writes `<PLAN_DIR>/audit/<LENS>.json` (`DP.json`, `CG.json`, `COV.json`, `TD.json`) and returns only the short summary.
4. Classify each lens's file after its completion notification with the contract's `audit-noop-detect.sh` call, re-dispatch a no-op lens exactly once against its re-cleared file, and on a second consecutive no-op run it inline, all per the contract's `## Pre-clear, classify, re-dispatch`.

The lenses:

- **Decomposition & dependency soundness (id prefix `DP`).** The highest-value lens, with no analog upstream or downstream. Attack the task graph: tasks placed in the same phase as "parallel" that actually share state, edit the same files, or consume each other's outputs; phase order that does not respect a real data or interface dependency; a frozen interface contract that two tasks interpret inconsistently; acceptance criteria that are not independently verifiable; a task in a parallel phase whose acceptance criteria run a repo-wide mutating or shared-state check (the project's lint script, typecheck or typegen, Playwright, a dev server) instead of one scoped to its own files, which races its siblings in the shared tree. Construct the concrete scenario where every per-task acceptance criterion passes yet the integrated result is broken. When another app test, existing or planned in any phase, exercises the path of a missing or mis-wired test setup (a mock handler, a base URL default, a seed), fix the setup in the task that owns it, through its acceptance criteria, or as a structural finding when the setup lands after the test that needs it, never with a new test row. Flag as `critical` any task that registers net-new files into `.gaia/manifest.json`, or that treats a file's absence from the manifest as `/update-gaia` drift: the manifest is release-generated only.
- **Contract grounding (id prefix `CG`).** Treat every file path, export subpath, type name, and function signature named in a task's interface contract or files-to-touch list as a factual claim, and verify each resolves against the real repo and `node_modules`. A contract that names a non-existent export, a wrong signature, or a hallucinated module is at least `major`, likely `critical`: the orchestrator will build against it and fail at integration.

- **SPEC coverage (id prefix `COV`, dispatched only when `SPEC_PATH` is set).** Build the matrix SPEC `flows` + `success_criteria` + `scope_boundaries` + `clarifications.answered` ↔ task acceptance criteria. Find the holes: a success criterion no task covers; a SPEC flow without exactly one closing-phase task naming its test path; a flow test created in a build phase; a task that drifts from or contradicts the SPEC's binding contract; scope the SPEC declared out-of-bounds that a task re-introduces. Whether a case, literal or layer is tested is the Test design lens's check, not this one. Read `<SPEC_PATH>` (interpolated) as the source of truth.
- **Test design (id prefix `TD`, always dispatched on a plan with a table).** Review `<PLAN_DIR>/tests.json` against `.claude/doctrine/testing.md` (Read it first, whole), the SPEC (or, spec-less, the plan's description), its audit directives, the documents the SPEC's `## Required reading` names, and the existing tests. Get the existing tests with `node .gaia/scripts/test-design/existing-tests.mjs --root <repo_root> --touched <file>`, `--touched` listing the source paths the plan's tasks touch, one per line. Build the matrix SPEC `flows` + `success_criteria` + `scope_boundaries` + `clarifications.answered` ↔ rows, one row per case: a compound condition one per part, and an order-of-checks row one per adjacent pair of checks (the doctrine's `## What to test`). Read `<SPEC_PATH>` (interpolated) as the source of truth, and for stated roles and wording also `AUDIT.md` beside it and the documents its `## Required reading` names; where the SPEC and one of those documents disagree on a role, name or wording, the SPEC's value is the stated literal. Name each check that fails:
  - a missing row, case or stated literal: a requirement with no row, a guard case with no test a task names below the closing flow, an order-of-checks pair with no test that passes every earlier check, fails both, and asserts the earlier of the pair refused, a signed or encrypted value (a cookie, a session, a token) with no test sending a forged or edited one, a role, accessible name or exact wording a task delivers, stated by the SPEC, an entry under `## Plan-time directives` in its `AUDIT.md` or a document its `## Required reading` names, that no existing or planned test at any layer, a flow test included, asserts as the stated literal (an assertion through an import of the app's own string counts as none; one story or route test may hold all of a page's specifics; a planned flow test counts only when its task doc names the literal for it to assert), `minor` unless it is a role or accessible name stated for a control, then `major`;
  - a wrong layer for what the row asserts, per the doctrine's layer rule, its unit-test conditions and its `**Shared guard.**` and `**Middleware guard.**` rules, such as a unit row asserting a request outcome or a middleware guard's refusal;
  - a duplicate within the plan: two rows asserting one behavior, where the fix keeps the row on the layer the doctrine's layer rule picks, except a per-outcome wiring row at another layer that the doctrine's `## What to test` keeps;
  - a test no requirement asks for;
  - a success-path route test for a happy path the closing flow test walks and asserts, unless the row asserts an effect the flow cannot observe; a flow observes an effect whose consequence a flow step asserts, such as a stored status that removes an item from a list the flow re-reads;
  - a test of a test double (a mock, a fixture, the Playwright fixture wiring, the plan's own Given builders) once another app test, existing or planned in any phase, exercises that path, judged by the doctrine's rule on what it can catch beyond that app test;
  - a planned test that duplicates or supersedes an existing test in the touched areas, which should be reuse, extend, change or retire;
  - a wrong or missing security flag, by the doctrine's `**Security row.**` kinds: an access row (sign-in and its refusals included), a forgery row, a secret row, or a retire or change row on an existing test of one of these kinds, flagged `none` or with another kind, or a flag on a row that is none of these. Judge each case by the doctrine's `**One kind per case.**`: a case of these kinds beside a case of another kind, `none` included, on one test, not split as it prescribes, is a finding whatever its flag, and its fix trims the row to the kind its flag names and adds a row for each other kind;
  - a security row whose owning task is not the latest task its test needs.

## 4.6a-ii. Refute the test-design findings

After the TD file classifies real, refute its material findings (`critical` or `major`); `minor` findings skip refutation and carry forward. Use the refutation pass of `.claude/skills/gaia/references/spec/audit.md` `### 7b-i. Refutation`: its refuter prompt and verdict schema, minus the `disposition` field and the SPEC-draft wording (the artifact under audit is the plan in `<PLAN_DIR>`, and the refuter also tries to refute from `.claude/doctrine/testing.md`). Dispatch one `general-purpose` Agent per material TD finding, all in parallel, keyed by `{ finding_id, findings_file }` with the findings file `<PLAN_DIR>/audit/TD.json` and no finding fields interpolated; above the spec audit's cap of 24 refuters, dispatch one batched refuter for the whole TD file instead, per that section's batched rule. Each verdict writes to `<PLAN_DIR>/audit/verdicts/<finding-id>.json` with the same `Bash`-at-the-main-checkout-path rule as a lens file; pre-clear it before dispatch. The thread reads the returned thin verdict lines, never the verdict files. A `refuted` verdict drops the finding; any other keeps it at its `corrected_severity`. When fan-out is unavailable, run each refuter inline on this thread.

## 4.6b. Apply findings

Read the findings from each `<PLAN_DIR>/audit/<LENS>.json` that classified real; this thread applies the fixes, so it reads the finding bodies.

- **Localized findings** (a wrong contract, a missing acceptance criterion, an uncovered flow): fold the fix directly into the affected `task-*.md` or `README.md` yourself.
- **Test design findings** (a row to add, change, trim or remove, a layer or flag to correct; a trim narrows an existing row to a subset of its cases and is a kind of change): apply them to `<PLAN_DIR>/tests.json` and the owning `task-*.md` `- Test:` lines yourself, then re-run the `plan.md` step 4.5 check so the table still verifies against the task docs.
- **Applied rows** (a `tests.json` row any lens's fix adds, changes or trims, the Test design lens's own included, and a row another finding is folded into): hold it to the Test design lens's checks above, in its new form, before applying it. A fold never changes the target row's `source`; a finding for another requirement is applied as its own row or recorded as an uncovered requirement. (A fold is any finding's fix, Localized ones included, that edits an existing row or its task-doc `- Test:` line rather than adding its own.) A row that fails one is reshaped when one change passes every check (a fix's offered trim counts as that change), else dropped, with the reason in the finding's recorded decision or, in auto-mode, in `## Audit notes`. Dropping an add leaves it out; dropping a change or trim leaves the row in its prior form, unless a Test design check bars that prior form too, and then the row is removed. When a drop or removal leaves a requirement or guard case with no row, record it as an uncovered requirement (a missing-row finding at the severity the missing-row check gives it, recommending a row every check passes, or in auto-mode in `## Audit notes`), not only as a dropped row; a security row is kept under the rule below, its `security` set to its kind if it is `none`.
- **Structural findings** (the phase graph is wrong, tasks need re-factoring across phases): re-spawn the planner rather than hand-patching the graph. Re-run `plan.md` step 4's dispatch with its optional `Correction` input set to the path of the surviving findings under `<PLAN_DIR>/audit/`, then re-run step 4.5 against the regenerated folder. This goes through the same `PLAN_DIR` and overwrites the flawed artifacts.

**Security rows.** A fix applied on this thread, from any lens or check, that would remove a security row (a row of the doctrine's kinds, or any row flagged) or clear a row's flag is not applied to that row unless the user rules it wrong on the review list. The row is kept and goes on the review list as its own item, even from a minor finding, recommending it be kept (in auto-mode, in `## Audit notes`).

**Interactive:** before the list prints, run the `**Applied rows**` check and collect the `**Security rows.**` items, so every row that check drops or reshapes, and every security item, joins the one list. Surface each material (critical or major) finding to the user before applying: print every one as text in the review-list format of `.claude/rules/user-questions.md` (`How a review list prints`), headed `Plan audit`, with its `Evidence` and its recommendation (apply the suggested fix, keep the current plan when the finding itself recommends keeping, drop or reshape the row for an `**Applied rows**` item, or keep the row for a `**Security rows.**` item), never its finding id, never a count, a summary, or a pointer to a findings file, and response-length or terseness preferences do not shorten the list; then ask one `AskUserQuestion` for the whole list (header `Plan audit`), per `.claude/rules/user-questions.md`'s review-list rule: `Accept all as recommended (Recommended)` or `Revise`. `Revise` asks which findings to change and what to change, unless a typed answer through the tool's own `Other` already says, then follows up only on those; every finding not named keeps its recommendation. Record every finding's decision before applying. The review list also carries one item per security-flagged `retire` row (`security` not `none`) in the table as it will stand once every fix applies, `minor` ones included, each on its own, recommending the retire as planned, whether or not any finding names it, but only for a test of code the plan keeps. A retire row for the security test of code the plan deletes needs no item: approving the plan approves it (the testing doctrine's **Security row** rule). Apply `minor` findings by default. **Auto-mode** (`auto_mode` true in `plan.md`): auto-apply unambiguous fixes; if a repair is ambiguous (more than one defensible fix), leave the plan unchanged and record the finding in a `## Audit notes` section appended to `README.md` so the orchestrator and user see it.

Then return to `plan.md` step 4.6c.
