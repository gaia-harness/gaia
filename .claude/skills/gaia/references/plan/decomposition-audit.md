# Decomposition audit

The `/gaia-plan` step 4.6 audit. The gauge in `plan.md` decides the decomposition, contract and SPEC coverage lenses; the test-design lens and its refuter run on every plan with a table. `.claude/skills/gaia/references/spec/lens-dispatch.md` is the lens contract: the shared preamble, the findings file each lens writes, and the pre-clear, classify and re-dispatch steps. This file owns which lenses run and how their findings are applied.

Contents: `## What the audit checks`, `## 4.6a. Dispatch the lens auditors`, `## 4.6a-ii. Refute the test-design findings`, `## 4.6b. Apply findings`.

## What the audit checks

A lightweight multi-agent audit of the **decomposition itself**: the one artifact neither the upstream SPEC audit (which ran before the plan existed) nor the downstream pre-merge Code Audit Team audit (which sees the executed diff) can inspect. It verifies that the task graph is a sound factoring of the work, that the frozen interface contracts resolve against the real repo, and that the SPEC's binding criteria are all covered, BEFORE a cold orchestrator burns execution cycles building against a flawed plan.

The audit stays narrow: four checks that exist only at plan stage. The decomposition, contract and SPEC coverage findings are checkable and binary, so they get no refutation pass; the test-design lens is the exception, because its findings are judgment (a layer, a duplicate, a flag), so each material one is refuted (`## 4.6a-ii`). It dispatches the same parallel `general-purpose` Agent primitive step 4 uses, so it works headless and in auto mode.

## 4.6a. Dispatch the lens auditors

1. Choose the lenses. The **Test design** lens always runs on a plan with a table, whatever the gauge. The **SPEC coverage** lens is dispatched only when `SPEC_PATH` was set in step 1a and the gauge runs the other lenses; those, **Decomposition & dependency soundness** and **Contract grounding**, run when the gauge says the plan is non-trivial. A SPEC-less plan's undispatched SPEC coverage lens is recorded not-applicable, never as a no-op.
2. Clear and create the findings directory `<PLAN_DIR>/audit/`, spelled repo-relative as the contract's pre-clear step does: `rm -rf <repo-relative PLAN_DIR>/audit`, then `mkdir -p <repo-relative PLAN_DIR>/audit` (for example `.notebook/plans/<PLAN-NNN>/audit`, or `.notebook/specs/<SPEC-ID>/plan/audit` for a spec-derived plan).
3. Spawn **one `general-purpose` Agent per lens, all in parallel** (one message, one Agent tool call per lens). Each prompt is the contract's shared preamble filled from its plan column (including its rule that, in a linked worktree, the lens writes its file with `Bash` at the main-checkout path (the clone's primary working directory, on any branch) and reads it back), with `<repo_root>` = `$PWD` and `<FINDINGS_DIR>` = `<PLAN_DIR>/audit/`, then the `LENS:` line and the lens's focus text below. Each lens writes `<PLAN_DIR>/audit/<LENS>.json` (`DP.json`, `CG.json`, `COV.json`, `TD.json`) and returns only the short summary.
4. Classify each lens's file after its completion notification with the contract's `audit-noop-detect.sh` call, re-dispatch a no-op lens exactly once against its re-cleared file, and on a second consecutive no-op run it inline, all per the contract's `## Pre-clear, classify, re-dispatch`.

The lenses:

- **Decomposition & dependency soundness (id prefix `DP`).** The highest-value lens, with no analog upstream or downstream. Attack the task graph: tasks placed in the same phase as "parallel" that actually share state, edit the same files, or consume each other's outputs; phase order that does not respect a real data or interface dependency; a frozen interface contract that two tasks interpret inconsistently; acceptance criteria that are not independently verifiable; a task in a parallel phase whose acceptance criteria run a repo-wide mutating or shared-state check (the project's lint script, typecheck or typegen, Playwright, a dev server) instead of one scoped to its own files, which races its siblings in the shared tree. Construct the concrete scenario where every per-task acceptance criterion passes yet the integrated result is broken. When another app test, existing or planned in any phase, exercises the path of a missing or mis-wired test setup (a mock handler, a base URL default, a seed), fix the setup in the task that owns it, through its acceptance criteria, or as a structural finding when the setup lands after the test that needs it, never with a new test row. Flag as `critical` any task that registers net-new files into `.gaia/manifest.json`, or that treats a file's absence from the manifest as `/update-gaia` drift: the manifest is release-generated only.
- **Contract grounding (id prefix `CG`).** Treat every file path, export subpath, type name, and function signature named in a task's interface contract or files-to-touch list as a factual claim, and verify each resolves against the real repo and `node_modules`. A contract that names a non-existent export, a wrong signature, or a hallucinated module is at least `major`, likely `critical`: the orchestrator will build against it and fail at integration.

- **SPEC coverage (id prefix `COV`, dispatched only when `SPEC_PATH` is set).** Read the `**Flow test.**` paragraph of `.claude/doctrine/testing.md` first. Build the matrix SPEC `flows` + `success_criteria` + `scope_boundaries` + `clarifications.answered` ↔ task acceptance criteria. Find the holes: a success criterion no task covers; a SPEC flow with neither exactly one closing-phase task naming its test path nor a `coveredFlows` entry in `tests.json`; a `coveredFlows` entry whose SPEC flow has a step the doctrine's `**Flow test.**` allow-list keeps on the flow, or a step none of the entry's rows owns, though a step that only reaches a page to see an owned literal or state needs no owner; a flow test created in a build phase; a task that drifts from or contradicts the SPEC's binding contract; scope the SPEC declared out-of-bounds that a task re-introduces. Whether a case, literal or layer is tested is the Test design lens's check, not this one. Read `<SPEC_PATH>` (interpolated) as the source of truth.
- **Test design (id prefix `TD`, always dispatched on a plan with a table).** Review `<PLAN_DIR>/tests.json` against `.claude/doctrine/testing.md` (Read it first, whole), the SPEC (or, spec-less, the plan's description), its audit directives, the documents the SPEC's `## Required reading` names, and the existing tests. Get the existing tests with `node .gaia/scripts/test-design/existing-tests.mjs --root <repo_root> --touched <file>`, `--touched` listing the source paths the plan's tasks touch, one per line. Build the matrix SPEC `flows` + `success_criteria` + `scope_boundaries` + `clarifications.answered` ↔ rows, one row per case: a compound condition one per part, and an order-of-checks row one per adjacent pair of checks (the doctrine's `## What to test`). Read `<SPEC_PATH>` (interpolated) as the source of truth, and for stated roles and wording also `AUDIT.md` beside it and the documents its `## Required reading` names; where the SPEC and one of those documents disagree on a role, name or wording, the SPEC's value is the stated literal. Name each check that fails:
  - a missing row, case or stated literal: a requirement with no row, a guard case with no test a task names below the closing flow, an order-of-checks pair with no test that passes every earlier check, fails both, and asserts the earlier of the pair refused, a signed or encrypted value (a cookie, a session, a token) with no test sending a forged or edited one, a destination the server sends the user or a request to (a redirect target, a callback URL) with no test sending one outside its allowed destinations, a role, accessible name, exact wording or attribute a task delivers, stated by the SPEC, an entry under `## Plan-time directives` in its `AUDIT.md` or a document its `## Required reading` names, that no existing or planned test at any layer, a flow test included for a role or accessible name, asserts as the stated literal (an assertion through an import of the app's own string counts as none; one story or route test may hold all of a page's specifics; a planned flow test counts only when its task doc names the literal for it to assert; walk the stated literals each task doc names for its builder, since a task doc naming one is no test), `minor` unless it is a role or accessible name stated for a control, or a field name or form target a native post sends, then `major`;
  - an `instructionKeys` entry whose requirement states what the app does: a missing row, at the severity the missing-row check gives it, its fix removing the entry and adding the row;
  - a wrong layer for what the row asserts, per the doctrine's layer rule, its unit-test conditions and its `**Shared guard.**` and `**Middleware guard.**` rules, such as a unit row asserting a request outcome or a middleware guard's refusal, or a story row flagged forgery that is not a `change` row on an existing story test or has no route or real-server forgery row for the same requirement, or a story access or secrets row with no route or real-server row for a guard the server enforces (the doctrine's `**Story security row.**`), or a heading whose text is loader data asserted only in a story given props (the doctrine's `## Served HTML`), its fix adding a route row asserting the loader returns that text and keeping the story row;
  - a stated mapping from a value the app reads to what the user sees with a value that has no case at the layer the doctrine's `## What to test` picks for the code that maps it, such as a mapping only a story given the mapped props asserts: the fix adds the missing cases there, and at a story that means one story row per value given the raw value, never a case table on one story row;
  - a page story, an error page's included, with no existing or planned test holding the doctrine's landmark check (`## Components, pages and stories`), `minor`: the fix adds the missing half to the test holding the page's heading, through its row or an `extend` row, or adds the landmark row;
  - a duplicate within the plan: two rows asserting one behavior, where the fix keeps the row on the layer the doctrine's layer rule picks, except a per-outcome wiring row at another layer that the doctrine's `## What to test` keeps. Two wiring cases of one rule's outcome at a layer other than its table's, on one row or several and whichever requirement each cites, are a duplicate: the fix moves each extra case into the table as a keyed row citing its own `source` and drops it from the wiring. So is a second case table for one rule at one layer, a table of a helper the rule's function derives (the actions a role is offered) included: the fix keeps the full table and drops the second, or trims it to the cases only that helper decides. A stated literal or state stays on its story or route test even when a real-server row asserts the same one: that row is trimmed to asserting the element carrying it is in the served HTML when the doctrine's `## Served HTML` makes that HTML the requirement, and dropped otherwise. A literal that is itself the served-HTML requirement by the doctrine's `## Served HTML` (a `<title>`, a meta description) stays on its real-server row, and a `**Served check.**` row the doctrine requires (served status and any `Location`) is never a duplicate of a route test, of another module's served check, or of a module's own refusal test (the doctrine's `**Shared guard.**`); the two-wiring-cases rule counts wiring cases within one module. A real-server row for a served error status that also asserts its page's heading or other content is trimmed to the status and any `Location`, never dropped for it;
  - a transition, status or role rule whose one case table lacks a case its requirement states (for a rule stated as sets, each case the doctrine's `## What to test` derives from them; one row per stating requirement is a sample), the case sitting only on another layer's row (a case another requirement states as a page effect, such as an alert shown, included) or, when that table is a unit test, the rule function's contract not taking the input that case varies, or whose table's boundary or exception case another layer's row of that rule repeats though another case produces the same outcome (the doctrine's `## What to test`): the fix moves the case into the table, adding that input to the contract when the table is a unit test, and trims the other-layer row to the per-outcome wiring row the doctrine keeps;
  - a case-table row whose `case` names its cases by class or sample (`every role`, `including an unknown tool`) instead of by value, the doctrine's `## What to test`: the fix lists each case's values from the requirements and the README contract;
  - a rule stated as sets with no `sets` entry in `tests.json`, or whose entry's axes leave out an action the rule governs or a role, relationship or status the requirements name, inside the set or out (`test-table.md` `## Row`): the fix writes or completes the entry, and step 4.5's `verify` then names each combination no row's `cells` hold;
  - a rule over roles or relationships and statuses whose status entry's `actors` leaves out a member inside an action's set or lists one outside it (`test-table.md` `## Row`): the fix corrects the map, and step 4.5's `verify` then names each actor that acts at no cell of a status;
  - a flow row step outside the doctrine's `**Flow test.**` allow-list (the journey through the happy path, a happy-path effect that takes several requests or sessions to stage, the page-less native posts of the happy path when the flow must work without JavaScript; a stated role or accessible name the journey locates or asserts a control by stays on the flow), such as a refusal a build task's row or another flow owns, however many requests or sessions it takes to stage, a native error post, a stated literal or state a lower-layer row owns, the SPEC flow's own statement naming it included, or a step that only reaches a page to see one, except a happy-path effect a flow step asserts, such as the sign-in redirect after sign-out, which stays on the flow even when the user sees it as a refusal (the success-path route test check below drops the lower-layer row instead): the fix trims the row to what only the flow layer shows and drops it when nothing is left, recording a SPEC flow left with no row in `coveredFlows`;
  - a test no requirement asks for, including a row whose source is a scope boundary or audit directive that directs the builder: its fix records that key in `instructionKeys`, removes every row citing it and drops their ids from each `coveredFlows` entry, removing an entry left with no rows and recording its flow as an uncovered requirement;
  - a success-path route test for a happy path the closing flow test walks and asserts, unless the row asserts an effect the flow cannot observe; a flow observes an effect whose consequence a flow step asserts, such as a stored status that removes an item from a list the flow re-reads;
  - a test of a test double (a mock, a fixture, the Playwright fixture wiring, the plan's own Given builders) once another app test, existing or planned in any phase, exercises that path, judged by the doctrine's rule on what it can catch beyond that app test;
  - a planned test that duplicates or supersedes an existing test in the touched areas, which should be reuse, extend, change or retire;
  - a wrong or missing security flag, by the doctrine's `**Security row.**` kinds: an access row (sign-in and its refusals, and an offer an access rule gates, a link included, whatever requirement the row cites), a forgery row (a redirect or callback target included), a secret row, or a retire or change row on an existing test of one of these kinds or made because a security requirement in its `source` forbids what the existing test asserted (then that requirement's kind, whatever the test's own kind), or a retire row for a test a flagged row from the same `source` subsumes (then that row's kind), flagged `none` or with another kind, or a flag on a row that is none of these. A `new`, `extend` or `reuse` row is judged by its own case, never by other rows' flags. A change row is judged by what the existing test asserted, not its changed form (a served `/` 200 check moved to `/login` once signed-out `/` redirects is access). A retire or change row citing a security requirement only because that requirement's work deletes or rewrites the tested code keeps the existing test's own kind (the home page's stories, when `/` stops being public), unless it is a retire that a flagged row from the same `source` subsumes. A test that puts a value a secrets requirement keeps off a surface onto that surface and asserts code there uses it tests what that requirement forbids, not code its work merely rewrites, so its retire or change row is secret (a browser test that reads a planted server-only API origin). A subsumed retire takes its flagged row's kind even when the requirement does not forbid what the test asserted (a test asserting the default API origin when none is planted, retired because a secret row proves the browser never takes the API origin, is secret). Judge each case by the doctrine's `**One kind per case.**`: a case of these kinds beside a case of another kind, `none` included, on one test, not split as it prescribes, is a finding whatever its flag, and its fix trims the row to the kind its flag names and adds a row for each other kind;
  - a flagged row's `caseKinds` (`test-table.md` `## Row`) giving a case a kind the check above would not, or leaving out a case its `case` names: `verify` checks only that the entries agree with each other and with the flag, so judge each entry by the case it names; the fix corrects or adds the entry and, when the kinds then differ, splits the row as the check above prescribes;
  - a security row whose owning task is not the latest task its test needs.

## 4.6a-ii. Refute the test-design findings

After the TD file classifies real, refute its material findings (`critical` or `major`); `minor` findings skip refutation and carry forward. Use the refutation pass of `.claude/skills/gaia/references/spec/audit.md` `### 7b-i. Refutation`: its refuter prompt and verdict schema, minus the `disposition` field and the SPEC-draft wording (the artifact under audit is the plan in `<PLAN_DIR>`, and the refuter also tries to refute from `.claude/doctrine/testing.md`). Dispatch one `general-purpose` Agent per material TD finding, all in parallel, keyed by `{ finding_id, findings_file }` with the findings file `<PLAN_DIR>/audit/TD.json` and no finding fields interpolated; above the spec audit's cap of 24 refuters, dispatch one batched refuter for the whole TD file instead, per that section's batched rule. Each verdict writes to `<PLAN_DIR>/audit/verdicts/<finding-id>.json` with the same `Bash`-at-the-main-checkout-path rule as a lens file; pre-clear it before dispatch. The thread reads the returned thin verdict lines, never the verdict files. A `refuted` verdict drops the finding; any other keeps it at its `corrected_severity`. When fan-out is unavailable, run each refuter inline on this thread.

## 4.6b. Apply findings

Read the findings from each `<PLAN_DIR>/audit/<LENS>.json` that classified real; this thread applies the fixes, so it reads the finding bodies.

- **Localized findings** (a wrong contract, a missing acceptance criterion, an uncovered flow): fold the fix directly into the affected `task-*.md` or `README.md` yourself.
- **Test design findings** (a row to add, change, trim or remove, a layer or flag to correct; a trim narrows an existing row to a subset of its cases and is a kind of change): apply them to `<PLAN_DIR>/tests.json` and the owning `task-*.md` `- Test:` lines yourself, a fix that adds an input to a rule function's contract also updates that contract in `README.md` and in every `task-*.md` that names it; then re-run the `plan.md` step 4.5 check so the table still verifies against the task docs.
- **Applied rows** (a `tests.json` row any lens's fix adds, changes or trims, the Test design lens's own included, and a row another finding is folded into): hold it to the Test design lens's checks above, in its new form, before applying it. For this check, a fold is any finding's fix, Localized ones included, that edits an existing row or its task-doc `- Test:` line instead of adding a row. A fold never changes the target row's `source`; a finding for another requirement is applied as its own row or recorded as an uncovered requirement. A row that fails one is reshaped when one change passes every check (a fix's offered trim counts as that change), else dropped, with the reason in the finding's recorded decision or, in auto-mode, in `## Audit notes`. Dropping an add leaves it out; dropping a change or trim leaves the row in its prior form, unless a Test design check bars that prior form too, and then the row is removed. A drop or removal of a sole row follows `**Sole rows**` below. When one leaves a requirement case or guard case with no row, record it as an uncovered requirement (a missing-row finding at the severity the missing-row check gives it, recommending a row every check passes and applied like any finding of that severity, or in auto-mode in `## Audit notes`), not only as a dropped row; a security row is kept under the rule below, its `security` set to its kind if it is `none`. Whenever a row is given a kind this way and has no `caseKey` and its `action` is not `retire`, also write its `caseKinds`: one entry per case its `case` names, all of the new kind (`test-table.md` `## Row`). Once the fixes apply, run `node .gaia/scripts/test-design/test-table.mjs flag-candidates --plan-dir <PLAN_DIR>`: each line is the id of an unflagged retire or change row sharing `file` and `source` with a flagged row, then those rows' kinds. Judge each by the security-flag check above and set the kind it earns (with `caseKinds` on a keyless non-retire row, per the sentence above), updating the row's README test-design row, listing it on its owning phase's `- Security writer:` line in `ORCHESTRATOR.md` (adding the line when the phase has none), and re-running the `plan.md` step 4.5 check. The review list has already printed, so in interactive mode each row given a kind prints on a follow-up review list as its own **Security rows.** item recommending that kind, and step 4.6c waits on it; in auto-mode, record it in `## Audit notes`. A retire row given a kind this way, for a test of code the plan keeps, also carries the **Interactive** paragraph's hold item (with its `Revise` drop) on that follow-up list.
- **Sole rows** (a row whose removal leaves a requirement key with no row, which step 4.5 refuses): list them with `node .gaia/scripts/test-design/test-table.mjs sole-rows --plan-dir <PLAN_DIR> --keys <keys file>`, the keys file holding what `bash .gaia/scripts/spec/requirement-keys.sh --spec <SPEC_PATH> --audit <its sibling AUDIT.md>` prints (drop `--audit` when that file is absent; `--description` for a spec-less plan), as step 4.5 builds them; each line is a row id and the keys only it covers. A fix or check that would remove one is not applied as written: keep the row, or reshape it when one change keeps its `source` and passes every Test design check. Removals apply one at a time, with `sole-rows` run again before each; a row it now lists is kept, and the **Outcome record** names it. That outcome is the finding's recommendation on the review list; in auto-mode, record it in `## Audit notes`. A fix that records the row's key in `instructionKeys` is applied as written: record the key, then remove every row citing it. When **Security rows.** below keeps one of those rows, record nothing.
- **Structural findings** (the phase graph is wrong, tasks need re-factoring across phases): re-spawn the planner rather than hand-patching the graph. Copy `<PLAN_DIR>/tests.json` to `<PLAN_DIR>/tests.before-correction.json` only when that file does not already exist (a re-spawn after a failed re-plan keeps the first snapshot, which still holds the rows the lossy table dropped), then re-run `plan.md` step 4's dispatch with its optional `Correction` input set to the path of the surviving findings under `<PLAN_DIR>/audit/`, then re-run step 4.5 against the regenerated folder. This goes through the same `PLAN_DIR` and overwrites the flawed artifacts. Then run `node .gaia/scripts/test-design/replanned-rows.mjs --before <PLAN_DIR>/tests.before-correction.json --after <PLAN_DIR>/tests.json`: each line is the id of a regenerated row no unmatched snapshot row equals on `file`, `title`, `layer`, `action`, `security`, `source`, `case`, `task`, `caseKey`, `held`, `deletes`, `cells` and `caseKinds` (each snapshot row matches at most one regenerated row, so a duplicate is listed), then the snapshot id of its prior form when that snapshot row keeps its id, `file` and `title`. Hold each to the **Applied rows** check, as a change from that prior form or, with none, an add, and re-run step 4.5 after any reshape, drop or return to the prior form; its items join the follow-up review list that carries the `lost:` and `reworded:` items (in auto-mode, `## Audit notes`). Then run `node .gaia/scripts/test-design/security-rows-lost.mjs --before <PLAN_DIR>/tests.before-correction.json --after <PLAN_DIR>/tests.json`: each `lost:` line names a source and kind the re-plan left short of security rows (dropped, unflagged, moved to another kind or swapped for another case under a new id), with the snapshot ids, and each missing row is held by the rule below. A non-zero exit is handled like a step 4.5 failure. Each `reworded:` line names a row kept under its id, source and kind with the same `file` and `title` and a different non-empty `caseKey`, old and new; an id reused by a row of another `file` or `title`, or by a row with no `caseKey`, reads as `lost:`. Also run the `flag-candidates` command of the **Applied rows** bullet against the regenerated table, and again after the restores, and judge its lines as that bullet says; the first run's items join the follow-up review list that carries the `lost:` and `reworded:` items, and the second run's new items print on their own follow-up list that step 4.6c waits on (in auto-mode, `## Audit notes`). Once every `lost:` and `reworded:` item is resolved, and every `flag-candidates` item, and every `replanned-rows` item, and step 4.5 passes, delete `<PLAN_DIR>/tests.before-correction.json` before step 4.6c.

**Security rows.** A fix applied on this thread, from any lens or check, that would remove a security row (a row of the doctrine's kinds, or any row flagged) or clear a row's flag is not applied to that row unless the user rules it wrong on the review list. A `new` row whose every case, once the fix applies, sits on another flagged row of the same kind, one whose `action` is not `retire` and which no fix on this thread removes, removes no security coverage: its item recommends removing it, and in auto-mode it is removed and recorded in `## Audit notes`. Any other such row is kept and goes on the review list as its own item, even from a minor finding, recommending it be kept (in auto-mode, in `## Audit notes`). A Structural re-plan's `lost:` line is held the same way: its item recommends restoring each missing row, picked from the line's snapshot ids by the case the regenerated table lacks. When the line's count is below the number of its ids, its keyed ids are all lost and its keyless ids are candidates; set aside each candidate a regenerated row matches on `file` and `title`, and when more candidates remain than the count less the keyed ids, the pick is ambiguous: it goes on the list as its own item with each candidate, and in auto-mode it is left unrestored and recorded in `## Audit notes`. A lost row whose code the regenerated plan deletes is a security retire of deleted code: its item recommends dropping it, and in auto-mode it is not restored and is recorded in `## Audit notes`. A `reworded:` line is not a loss: its item, on the follow-up review list the `lost:` items print on, quotes the old and new case and recommends keeping the row as regenerated, and `Revise` restores the old case as a lost row; in auto-mode the row is kept and the old and new case are recorded in `## Audit notes`. The `lost:` items exist only after the re-plan and compare have run, so in interactive mode they print on a follow-up review list after the re-plan, each as its own item with the recommendation above, and step 4.6c waits on it; a restore from it that fails step 4.5 goes on the second review list below, after the follow-up list. A regenerated row on the same `file`, `title` and `caseKey` whose `security` is `none` gets the snapshot's `security` back, in `tests.json` and its README row; a regenerated row that carries a different non-none kind keeps its kind, and the snapshot row is added beside it under a new id like any other; any other is added under an id the regenerated table does not use, by `test-table.md` `## Procedure` steps 7 to 10 against the regenerated plan, with its README row. Either way, the owning task's phase entry in `ORCHESTRATOR.md` lists it on its `- Security writer:` line, adding the line when the phase has none. A restored keyless non-retire row carries the snapshot row's `caseKinds`; a re-flagged one gets one entry per case its own `case` names, all of the snapshot's kind. Every restore re-runs step 4.5, and the compare runs again after the restores; when 4.5 fails, undo the restore and, after the first list's fixes apply, print a second review list holding only such rows, each as its own item, not restored, recommending the user restore it by hand, and step 4.6c waits until the user has restored it or ruled it wrong, and step 4.5 passes (in auto-mode, stop like a step 4.5 failure, naming the row, rather than finishing on a prose note, since no mechanical hold carries a row absent from the table). In auto-mode, restore it and record it in `## Audit notes`.

**Interactive:** before the list prints, run the `**Applied rows**` and `**Sole rows**` checks and collect the `**Security rows.**` items, so every row those checks keep, drop or reshape, and every security item except a re-plan's `lost:`, `reworded:` and `replanned-rows` items (which print on their own follow-up list after the re-plan) and the `flag-candidates` items (which print on their own follow-up list after the fixes apply), joins the one list. Surface each material (critical or major) finding to the user before applying: print every one as text in the review-list format of `.claude/rules/user-questions.md` (`How a review list prints`), headed `Plan audit`, with its `Evidence` and its recommendation (apply the suggested fix, keep the current plan when the finding itself recommends keeping, drop or reshape the row for an `**Applied rows**` item, keep or reshape it for a `**Sole rows**` item, or what `**Security rows.**` recommends for its item), never its finding id, never a count, a summary, or a pointer to a findings file, and response-length or terseness preferences do not shorten the list; then ask one `AskUserQuestion` for the whole list (header `Plan audit`), per `.claude/rules/user-questions.md`'s review-list rule: `Accept all as recommended (Recommended)` or `Revise`. `Revise` asks which findings to change and what to change, unless a typed answer through the tool's own `Other` already says, then follows up only on those; every finding not named keeps its recommendation. Record every finding's decision before applying.
