# Workspace Standard For Apps And Packages

GAIA names one pnpm workspace layout and supports that layout rather than any layout: apps live in `apps/<name>`, libraries in `packages/<name>` once two consumers share them, and the React app sits at `apps/web` with its source in `apps/web/app`. Every registered workspace member gets the workflow, audit and merge gates; only a member that declares GAIA's web stack gets the frontend rules, scaffolding and generated settings. An existing 2.x project crosses to the layout through `/update-gaia` without losing work.

## Decisions

**Why one standard.** pnpm sets no layout, so the convention is GAIA's own. A harness that assumes a single app package leaves a mobile app, an API or a shared library either invisible to the gates or reviewed through React lenses, and a library change that breaks two consumers goes uncaught. Fixing one shape while few projects carry the old path costs far less than supporting arbitrary shapes later. The procedure for adding a member, with worked examples, is [[Package Descriptor#Adding an app or package]]; the rule itself is in `.claude/rules/coding-guidelines.md`.

**The web member is found by stack, never by name.** The descriptor's optional `stack` field marks a web-stack member, and absent means not web, so a wrong default on a library never leaks web rules. The registry stays a plain name and path list. Scaffold, rename, the env seed, wiki classification, the audit's web lenses and the rest of the frontend-only tooling key on that field, so an adopter who keeps another app name works unchanged and several web-stack members are allowed. Scaffold and rename take `--package <name>`: with no flag they use the only web-stack member whatever the working directory, with several they refuse and name the candidates, and given a non-web member they exit `CONFIG_INVALID` and change nothing. The audit member keeps its name `code-audit-frontend`: it is a member name, not a path, and renaming markers, digests and status contexts buys nothing.

**Generated settings are web-stack or opt-in.** A full generated settings file per member costs tens of kilobytes and hundreds of lines, rewritten on every root settings change, and only a session launched inside that member reads it. So a web-stack member, or one whose descriptor sets `generatedSettings` to `true`, gets the full file, and every other registered member gets a one-hook stub. Claude Code reads shared settings only from the launch directory, so no root hook fires in a session launched inside a member; the stub warns at session start that GAIA's guards are off and to launch from the repo root. It restores no guard, is never written over a hand-written settings file, and a missing or edited stub draws a warning, not a failure. [[Package Descriptor#Launch scope]] owns the mechanics.

**Structure is enforced by support and a warning, never by failure.** `gaia fitness check` warns on a workspace member absent from `.gaia/packages.json` and names a member at a path the registry refuses as unregistrable; both are warnings, exit 0 under default options and can be suppressed. No structure check reads inside a member, and none fails a customized project. [[Customizing GAIA#Structure tolerance]] states the adopter-facing side.

**The gate runs across the workspace instead of filtering by change.** Root `typecheck`, `lint` and `test:ci` run recursively with `--if-present` and `--no-bail`, so a consumer broken by a library change fails the gate and every failing member is reported in one step. A changed-since filter was rejected because it needs a base ref and workspace links a project may lack. `test:ci` is each member's own non-watch script, taking no arguments, so a member on another test runner never receives a Vitest flag. `.gaia/scripts/gate-member-warnings.sh` warns, exiting 0, on a member with tests but no `test:ci` or TypeScript but no `typecheck`. Playwright, the build and the dev smoke stay web-only, and pre-commit stays per-owner. The cost is a slower gate on a large workspace. [[Quality Gate]] owns the steps.

**The default audit member reviews non-web members, with the web lenses off.** The roster's default member owns `apps/**` and `packages/**`, so every member under those trees has an owner; a registered member elsewhere, such as an adopter's `infra`, takes a default-member claim in `.gaia/audit-ci.yml`. A non-web path keeps the security dimension and every lens that is not web-specific; `.gaia/scripts/audit-resolve-scope.sh` prints the lenses for each path by stack, and an unreadable registry turns every lens on. A new shipped member for non-web code was rejected: it would add an agent file and a marker for no extra coverage on a stock project, and an adopter can still add their own claimant.

**The crossing reuses the ordinary merge.** A three-way merge with no rename awareness reads every moved path as an upstream deletion and would offer to delete the adopter's app, and the first crossing runs the old installed skill, which knows nothing of the move. So the 2.4.0 migration note is blocking: the installed skill stops at its selector and the note owns the hop from any 2.x baseline. The note drives `gaia update crossing` from the verified target bundle: `preflight` checks the tree and changes nothing, `move` relocates the app with `git mv` and edits the registry and the workspace packages list entry by entry, `rekey` rewrites a copy of the baseline bundle, each deferred entry's baseline and the decision log from the old root to `apps/web/`, and `roster` rewrites the audit roster. The ordinary three-way walk then runs against the rekeyed baseline, so every key matches and the existing merge table keeps its three promises with no new merge logic: a deleted file stays deleted, a changed file merges, an unmanifested file is untouched. The adopter's packages list keeps every entry they added: only the old app entry is replaced by `apps/*`, and `packages/*` is added when absent. The move and the merge land as one commit under the merged hooks, because a rename-only commit would run the old pre-commit hook against a tree that does not build. The resume path is one preflight arm, the old root absent with the app already at `apps/web` on a manifest still keyed on the old root, which also serves an adopter who moved the app by hand. [[Update Workflow]] owns the adopter-facing description.

**The old root stays retired.** `.gaia/scripts/check-retired-paths.sh` treats the old app root as a retired path root, including in rule bodies, rule `paths:` frontmatter and every tracked Markdown file, so a citation of it in a tracked doc fails the check; `.gaia/retired-paths-allowlist.tsv` holds the frozen history files and migration notes that keep it on purpose.

**Proof.** The CLI suites cover the crossing verbs, the fitness rules and the package-target resolution; bats suites cover web-stack reach (rule locations, scaffold and rename refusals, settings stubs), the retired root and per-gate witnesses at `apps/web`; the distribution suite proves a fresh project from a staged bundle, the crossing's move and edits on a monorepo fixture and a stock tree, per-member pre-commit and audit reach, and the workspace gate catching a type and a test break in two consumers.

## Divergence

- **The attended live crossing is not proven on this branch.** It was dropped by the maintainer and is tracked separately, so these stay unproven here: the crossing commit end to end in a live session (the pre-commit hook ran for it, every `.claude/settings.json` write went through the settings write guard's ask, exactly one commit sits above the base, update decisions apply at the new path, and no hook was bypassed), a later update on a customized crossed project keeping its customizations with nothing restored, and a resumed crossing finishing at the same tree as an uninterrupted one. The deterministic crossing steps the note calls are tested directly; the note's own prose rests on that unrun live session.
- **Cross-package impact in audit is out of scope.** An audit does not read a changed library's consumers; that is tracked separately. The quality gate covers consumers instead.
- **The stock Dockerfile copies only the app,** so it builds no member that consumes a workspace library; an adopter who adds one extends it.
