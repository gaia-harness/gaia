# GAIA Plan

`/gaia-plan [description]` plans a complex feature using GAIA's [[Task Orchestration]] pattern, without implementing anything. The skill lives at `.claude/skills/gaia/references/plan.md` (dispatched by the `/gaia-plan` command, which reads this reference).

## Steps

1. **Get description.** A leading `auto` in `$ARGUMENTS` is the mode token (always, as in `/gaia-spec`): it is stripped before the SPEC reference is read and selects the non-interactive branches, and `/gaia-plan auto` with nothing after it aborts with a re-invoke line. Use the remaining `$ARGUMENTS` if provided; otherwise ask "What do you want me to orchestrate?" and wait. A bare `SPEC-NNN` id (the form [[GAIA Spec]] passes when it chains into planning) resolves the plan from that SPEC's `.notebook/specs/SPEC-NNN/SPEC.md`, reading its sibling `AUDIT.md` too when the audit produced one, no path or intent text needs to travel in the invocation.
2. **Pick the planner model.** The planner's model is pinned at spawn, so it runs on a top-tier model even when the session is on Sonnet. Opus and Fable are both top-tier planning models. If the session is on Opus or Fable, the planner inherits the current model. When the run is non-interactive (a headless or automation context with no interactive user to prompt, or the `auto` token), the planner defaults to Opus without a prompt. Otherwise (the session is on Sonnet, Haiku, or another lesser model) ask via `AskUserQuestion` (header `Model`) which model should plan, with "Use Opus (Recommended)" as the default option, "Use Fable" as a second top-tier choice, and "keep the current model" as the alternative.
3. **Spawn the planner.** Launch one `general-purpose` Agent (the only planner, no parallel writers or decision pass) with the chosen model and a short prompt that passes only the plan-specific inputs (plan folder, SPEC and AUDIT paths or `unset`, branch id, feature description); the planner reads its instructions from `.claude/skills/gaia/references/plan/planner.md` and builds the plan files: per-task docs, `README.md` (task graph + frozen interface contracts) and the parts file `orchestrator-parts.md`; the renderer then writes `ORCHESTRATOR.md` (execution playbook) and `KICKOFF.md` (the cold-start prompt) from `.claude/skills/gaia/references/plan/orchestrator-template.md` and the parts file. The planner is a leaf sub-agent: it investigates with parallel tool calls and writes the files, and it does not spawn sub-agents (see [[Task Orchestration#Topology]]). See [[Task Orchestration]] for the artifact contract. A planner that runs heavy on context yields to a fresh planner through a handoff file; the dispatch chain is bounded by `gaia_context_yield_limit` (see `.claude/skills/gaia/references/plan.md`, `#### Planner yield`).
4. **Plan review.** After the planner returns and its artifacts pass the existence check, a three-lens review of the decomposition itself runs automatically with no prompt. A trivial plan (one or two tasks in a single phase with no cross-task contract) skips it; anything with parallel tasks, several phases or a shared frozen contract runs it. It never blocks the handoff. Each lens writes its findings to a file under the plan folder that is checked after it finishes, so a silent lens cannot pass as a clean decomposition (see `.claude/skills/gaia/references/spec/lens-dispatch.md`). The three parallel `general-purpose` lenses are decomposition and dependency soundness, contract grounding (every file, export, type and signature a task contract names resolves against the real repo and `node_modules`), and SPEC coverage (dispatched only when the plan derives from a SPEC; see [[GAIA Spec]]). There is no refutation pass: the findings are checkable rather than severity-debatable. A structural finding re-spawns the planner with the findings as a correction directive; the main thread folds each localized finding into the task docs, and `.gaia/scripts/spec/drop-check.mjs` refuses a fix that drops an acceptance criterion with no destination or rewrites one no fix traces. Interactive surfaces each material finding before applying; auto mode applies the unambiguous ones. `.claude/skills/gaia/references/plan/decomposition-audit.md` owns the lenses and the fold.
5. **Offer the test stage.** After the review and the usage record close the `gaia-plan` run, one question (header `Test stage`) offers the test stage: `Run the test stage (Recommended)` or `Skip`; auto mode and non-interactive runs take Run, and a spec-less plan is offered it too. Run invokes the `gaia-test` skill, which opens its own usage run ([[Test Stage]]). Skip writes the skipped `TEST-STAGE` record, and with it the rule-written security tests are skipped.
6. **Hand off.** Print a short summary of the plan, then a fenced one-line resume prompt (`Read /abs/path/to/<plan-dir>/KICKOFF.md and execute it.`, where `<plan-dir>` is `.notebook/plans/PLAN-NNN/` or the colocated `.notebook/specs/<SPEC-ID>/plan/`). The skill prints the prompt as a fenced code block, then a single trailing `Type /clear and paste the prompt above.` line.

## Plan mode is not this skill

The harness's own plan mode (`ExitPlanMode`, a single markdown written to `~/.claude/plans/`) is a different mechanism from `/gaia-plan`. Plan mode can wrap a `/gaia-plan` invocation, but the skill's real deliverable is still the artifact set under `.notebook/plans/` (or the colocated SPEC folder) plus the KICKOFF resume prompt, not a plan-mode markdown. Follow the skill's Steps above even when plan mode wraps the call.

## Orchestrator contract

`ORCHESTRATOR.md` pins each task sub-agent to `model: sonnet` by default, decoupling execution from the orchestrator's own session model, since the spec and plan audits resolve the complexity upstream so execution runs on the cheaper model. The planner escalates a specific phase to Opus only when it names a genuinely deep-synthesis reason. `ORCHESTRATOR.md` also mandates a brief **final summary** before awaiting merge confirmation: its fields are listed under "Final summary" in `.claude/skills/gaia/references/plan/orchestrator-template.md`. A few lines, not a recap of every change. The close runs in two halves around the merge. After the user confirms the PR is ready to merge, consolidation produces a verified `SUMMARY.md` and the wiki promotion step acts on it, both before the merge. After the merge is confirmed, the post-merge close removes a spec-colocated plan's `SPEC.md` and `AUDIT.md` once `SUMMARY.md` re-verifies, and the archive step runs: a spec-less plan's folder is kept, reduced to `SUMMARY.md` with its `RUNNING` sentinel cleared, gated on `usage.sh represented` finding the plan's `gaia-plan` close on the usage ledger, which with the notebook catalog is the whole durable record that survives; a spec-colocated plan deletes only its own `plan[-N]` subfolder once the parent SPEC's `SUMMARY.md` exists. See [[Task Orchestration]] for the full retention mechanics.

## Ledger status and closure

A plan's catalog row (or, for a spec-colocated plan, the parent SPEC's catalog row) carries a status, allocated at `ready` and age-anchored on `merged_at`. The orchestrator's post-merge close stamps the row `merged` together with the confirmed `pr_number`, and the pre-flight sweep of both `/gaia-spec` and `/gaia-plan` is the backstop for a merge that happened outside an orchestrator: it reconciles the catalog, consolidates folders never consolidated, and age-reaps through the retention helpers described in [[Task Orchestration]]. `.claude/skills/gaia/references/spec/lifecycle.md` owns the steps.

Reaching the wiki is offered-then-gated rather than default-on: the consolidation step stamps a spec-less plan's `SUMMARY.md` with `wiki_promote_default: ask` and `wiki_promote_targets: [decisions]`, so a human is asked before the audit whether the plan's outcome is worth a wiki page. A declined promotion, or an `ask` with no human present, is recorded in `PROGRESS.md` and nothing is deferred or drained later. This is deliberately asymmetric with a SPEC's default-on promotion, since not every plan produces wiki-durable knowledge. A SPEC carries no target list of its own, so consolidation derives its `wiki_promote_targets` from what shipped, and `summary-verify.sh` fails a `yes` SUMMARY whose list is empty rather than letting promotion no-op.
